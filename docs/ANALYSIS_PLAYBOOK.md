# 分析排查手册

这份手册不是讲业务功能，而是讲：

> 当你遇到“到底是什么起作用”“为什么会绕路”“这个依赖是不是真的必要”这类问题时，应该怎么拆、怎么测、怎么收敛。

这份文档来自本项目在 HTTP runtime / 登录态最小化实验中的真实经验。

---

## 一、先问清楚：你到底要证明什么

很多分析会绕路，不是因为技术不行，而是因为一开始问题就没拆清楚。

先把目标写成下面三类之一：

### 1. 证明“能跑”

比如：

- 这个接口能不能通
- 这个文件能不能转写成功
- 这个环境能不能启动服务

### 2. 证明“最小必要条件”

比如：

- 哪个 cookie 真正起作用
- localStorage 到底要不要
- Playwright 是不是必须

### 3. 证明“某个依赖能不能移除”

比如：

- 没有 Playwright 能不能跑
- 不依赖旧项目目录能不能跑
- 不依赖 storage state 全量内容能不能跑

---

## 二、固定真实运行配置

在开始任何实验前，先确认“你实际上跑的是什么”。

至少要打印这些：

- 当前分支
- 当前 `.env`
- 当前 backend
- 当前 auth 文件路径
- 当前项目根目录
- 当前输入文件路径

如果这一步不做，很容易出现：

- 以为测的是新代码
- 实际跑的是旧配置
- 以为在测当前仓库
- 实际读的是别的目录

### 建议

每次实验前，先把这些信息打印出来，作为实验记录的一部分。

---

## 三、把问题拆成四层

以后遇到类似问题，先按这四层拆：

### 1. 配置层

问：

- 实际 `.env` 指向哪里？
- auth 文件从哪里读？
- backend 是什么？

### 2. 认证层

问：

- 有哪些认证材料？
- 哪些只是“存在”？
- 哪些是“真正必要”？

### 3. 运行时层

问：

- 是登录需要 Playwright？
- 还是主链路实现本身依赖 Playwright？

### 4. 业务链路层

问：

- 你测的是 quota？
- 还是 oss token？
- 还是整条 upload → start → poll → export？

如果这四层不拆开，问题会混在一起，导致你不知道到底是哪一层卡住。

---

## 四、标准实验流程

这套流程可以直接复用。

### Step 1：先跑通原始链路

先确认：

- 原方案确实能稳定成功
- 成功标准是什么
- 最终产物是什么

没有基线，后面的优化都不可信。

---

### Step 2：一次只改一个变量

不要同时改：

- cookie
- backend
- 文件
- 运行环境
- 网络条件

一次只动一个变量。

例如：

- 先全量 state
- 再 cookie-only
- 再 ticket-only
- 再 clean venv
- 再 backend 切换

这样结论才可信。

---

### Step 3：先做最小探针

不要一上来改整套系统，先做探针脚本。

例如先测：

- quota
- `record/oss/token/get`

因为这两个最容易回答：

- 认证是否成立
- 最小材料是否够用

---

### Step 4：再拉长到完整链路

探针通过后，再按顺序拉长：

1. upload
2. heartbeat
3. start
4. poll
5. read
6. export
7. delete

不要跳步骤。

---

### Step 5：一定做干净环境复验

这是最容易被忽略的一步。

必须问自己：

> 这个结论是不是环境幻觉？

建议至少做一次：

- 新 venv
- 去掉全局包影响
- 去掉旧目录依赖
- 去掉多余 runtime

如果在干净环境里还能成立，结论才真正站得住。

---

### Step 6：把结论固化成脚本和文档

不要只停留在“我测过”。

至少要落成：

- 一个实验脚本
- 一份计划文档
- 一份结论记录

否则过几天就会失真。

---

## 五、如何判断“存在”不等于“必要”

这是最常见误区。

例如一个 storage state 里可能同时有：

- cookies
- origins
- localStorage
- 分析字段
- 跟踪字段

它们都在文件里，不代表它们都重要。

正确做法是：

### 先做“删减实验”

例如：

- 全量
- cookie-only
- qianwen-only
- ticket-only
- origins-only

然后看哪一步开始失败。

谁删掉就失败，谁才更可能是真正必要条件。

---

## 六、如何判断“登录依赖”和“实现依赖”

这两个很容易混淆。

### 登录依赖

比如：

- 登录页面需要浏览器
- 人工扫码需要 Playwright

### 实现依赖

比如：

- 主链路代码写死了 `playwright.request.new_context(...)`

你要分清：

- 是“业务本身必须要浏览器”
- 还是“代码当前只是这么写的”

这两者完全不是一回事。

---

## 七、成功标准一定要写清楚

很多分析失败，不是实验失败，而是成功标准没写清楚。

你必须明确你要的是：

- 一个接口返回 `200`
- 还是拿到 `recordId`
- 还是拿到 `batchId`
- 还是最终导出 Markdown
- 还是下载结果和落盘文件一致

成功标准不清楚，就会一直停留在“看起来差不多”。

---

## 八、本项目已经验证过的一套方法

在本项目里，以下分析路径已经被证明有效：

1. 先确认真实运行配置
2. 隔离 storage state 内容
3. 找到最小 cookie
4. 在无 Playwright venv 中复验
5. 先做 probe
6. 再做完整链路
7. 再把实验脚本能力抽成正式 backend
8. 最后做 service 级回归

这个顺序很重要。

---

## 九、以后你可以直接套用的提问模板

碰到类似问题，先问自己这几句：

### 1. 我要证明什么？

- 能跑？
- 最小必要条件？
- 移除某个依赖后还能不能跑？

### 2. 我现在实际跑的是什么？

- 分支？
- `.env`？
- auth 文件？
- backend？

### 3. 成功标准是什么？

- 200？
- 一个 ID？
- 还是整条业务链完成？

### 4. 我这次只改了一个变量吗？

如果不是，就先停下来，收窄变量。

### 5. 我有没有做干净环境复验？

如果没有，结论不要下太满。

---

## 十、最后一句话

以后再遇到“到底哪个因素起作用”的问题，先做三件事：

1. **确认真实配置**
2. **做最小剥离实验**
3. **做干净环境复验**

只要你把这三步做扎实，弯路会少非常多。
